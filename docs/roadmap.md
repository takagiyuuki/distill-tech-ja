# distill-tech-ja — 学習ロードマップ

複数の技術メディア（HackerNews / Zenn / AWS Blog など）を **言語を問わず日本語で要約して日付別に配信する**アグリゲータ。核は**要約**であり、翻訳はソース言語が日本語でない場合のみ走る条件付き前処理。HN は本文を要約せず**タイトル＋コメント論点要約**でエントリを構成する。生成完了時に自分用 Slack/Discord 通知を飛ばす。

> 設計の正典: ドメイン用語は [`CONTEXT.md`](../CONTEXT.md)、覆しにくい設計判断は [`docs/adr/`](./adr/) を参照。本ロードマップと食い違ったら正典側を優先。

- リポジトリ名: `distill-tech-ja`
- サブドメイン: `distill-tech-ja.yukit.dev`（運用が育ってUIに凝りだしたら、短いブランド名へリネームしてよい。GitHub rename は旧URLから自動リダイレクトされ安全）

## 技術選定（確定）

- 推論: Workers AI のみ（無料枠 10,000 Neurons/日、超過分 $0.011 / 1,000 Neurons）
- スタック: Hono + Cloudflare Workers + Cron Triggers + D1（想定）+ Workers AI
- 開発: Claude Code（運用ルールは後述）
- VCS: jj（既存ワークフロー）/ GitHub `takagiyuuki`

## 設計原則（著作権・運用）

- **本文・コメント原文は載せない。** 自前生成の要約＋原典リンクのみ。
- 取得時は対象サイトの robots.txt / 利用規約を尊重。
- 要約は元表現をなぞらない短いものにする（プロンプトで明示）。
- これが catnose 氏プロダクトとの差別化（複数ソース＋コメント要約）と安全な公開の両立点。

## 開発方針：Claude Code の使い方

**大原則: コードは自分で書く。Claude Code に全実装を委ねない。** 学習が主目的のため、エージェントに丸投げすると「動くが理解していない」状態になり、転職活動で語れない。Claude Code は設計の壁打ち・調査・レビュー・デバッグ相談に限定して使う。

具体的な運用ルールは **リポジトリ直下の `CLAUDE.md` を参照**（Claude Code が自動で読む）。このロードマップでは重複を避け、各フェーズの「Claude Code の使いどころ」のみ記載する。

補足:

- **プランモード**（Shift+Tab 2回）を、スキーマ設計や複数ファイルに跨る変更で活用する。「計画→自分でレビュー→自分で書く」の順。
- formatter/linter は CLAUDE.md ではなく hooks（Biome + lefthook）で強制する。CLAUDE.md は方針・役割の指示に絞る。

## Phase 1: HN 取得（1〜2日）

**ゴール**: トップ記事のタイトル・URL・上位コメントを取得し JSON で返す。

**学ぶこと**

- **Firebase ＋ Algolia ハイブリッド取得**（ADR 0002）。理由は Workers 無料プランの**外部サブリクエスト上限50/実行**。
  - トップ記事ID: Firebase `https://hacker-news.firebaseio.com/v0/topstories.json`（「今のトップ」の権威）。
  - 各記事＋コメントツリー一括: Algolia `https://hn.algolia.com/api/v1/items/{id}`（1リクエストで本文付き・ネスト込み）。
  - これで外部 fetch は「1 ＋ 記事数」≒11回に収まる。Firebase の `item/{id}` 再帰（コメント1件ずつ fetch）は subrequest 50 を超えるため使わない。
- `Promise.all` での並列取得と件数制限。

**作るもの（自分で書く）**

- 上位 N 件（運用目標は8〜10件、スコア足切り。閾値・件数は**設定値で外出し**）の記事メタ＋コメントツリーを集約する関数。
- `/api/today` で整形済み配列を返す（Phase 2 の要約品質を目視チェックする窓にもなる）。

**つまずきポイント**

- コメント入力範囲は「トップ＋第1階層返信を数件」を初期値に、生成結果を見て深さ・件数を調整（設定値）。
- `url` の無い記事（Ask HN 等）はコメント論点要約のみで成立する（本文要約しないため Phase 3 待ちにならない）。
- 外部サブリクエスト50に注意（Algolia 1記事1リクエストで収める）。過剰並列を避ける。

**Claude Code**: HN APIのレスポンス構造を調査させる。書いた取得関数をレビューさせ「並列数・エラーハンドリングの懸念」を指摘してもらう。

**完了の目安**: `/api/today` が記事＋コメント配列を返す。

## Phase 2: Workers AI 翻訳・要約（2〜3日）★中心

**ゴール**: HN の**タイトル＋コメント群**を Workers AI で日本語に要約（英語なら翻訳を前段に挟む）。本文要約は当面行わず、発行元フィード（Phase 7）で初登場。

**学ぶこと**

- Workers AI binding（`wrangler.jsonc` の `ai`）と `env.AI.run()`。
- モデル選択。**Gemma 3 を本命**、無料枠を超えそうなら **GLM-4.7-Flash** に切替（モデルは設定値で外出し）。日本語品質を実測比較。
  - コンテキスト長は 128K 級で潤沢。**コメント深さを縛るのは Neuron コストとサブリクエスト**であってコンテキスト長ではない。
- プロンプト設計を分割: コメント論点要約 / （英語ソース向け）タイトル翻訳 / （Phase 7）記事要約。HN の主役はコメント論点要約。
- ダッシュボードで Neuron 消費を測り、無料枠に収まるか確認。

**作るもの（自分で書く）**

- `summarizeComments()`（主役）/ `translateTitle()`（英語ソース時）。`summarizeArticle()` は Phase 7 で本文が入ってから。
- Phase 1 の出力に組み込み、日本語要約付き JSON を返す。

**つまずきポイント**

- コンテキスト長は 128K 級で余裕。切り詰めの主目的は Neuron 消費の抑制（コスト）。
- 要約が元表現をなぞらないようプロンプトで明示（著作権設計＝ADR 0003 と直結）。
- JSON 出力の安定化とパース失敗ハンドリング。
- 日本語品質はClaude/GPT級でない。実用十分か自分の目で判断。

**Claude Code**: プロンプト設計の壁打ちが主役。「コメント群から論点を抽出する指示文、どう書けば原文をなぞらず要約できる？」を相談。モデル選定の比較観点も相談。**ただしプロンプト文・呼び出しコードは自分で書く。**

**完了の目安**: 英語記事→日本語タイトル・記事要約・コメント要約が返る。

## Phase 3: 本文抽出（1〜2日）

**ゴール（後ろ倒しの拡張）**: 第三者ページの HTML から本文を抽出し、本文ベース要約を可能にする。**Phase 1〜6 を HN（タイトル＋コメント）で貫通させた後に着手**する独立拡張。ADR 0001 の通り、HN のコア機能には不要。

**学ぶこと**

- **Workers には `DOMParser` が無い**。`@mozilla/readability` / `defuddle` は DOM 前提でそのまま動かない。
  - 主軸は **HTMLRewriter**（Workers ネイティブのストリーミングパーサ）でセレクタ抜き取り（`<article>`/`<main>` を拾い chrome を捨てる）。
  - 全文スコアリングは原理的に不可。セマンティックHTMLのサイト（公式ドキュメント・個人ブログ等）で効く。
  - 取れない/薄い場合はフォールバック（本文なし扱い）。
- robots.txt 尊重と取得失敗時フォールバック。

**作るもの（自分で書く）**

- `extractArticleText(url)`: fetch→抽出→`summarizeArticle()` へ。

**つまずきポイント**

- サイトごとに構造がバラバラ。完璧を狙わず「抽出失敗ならタイトルのみで要約」にフォールバック。
- ペイウォール・JSレンダリングは取れない。諦めてフォールバック。
- タイムアウト注意（Cron実行なので多少遅くても可）。

**Claude Code**: 抽出ライブラリのWorker互換性を調査。フォールバック設計の妥当性をレビュー。

**完了の目安**: 大半の記事で本文ベース要約。取れない記事でも落ちない。

## Phase 4: D1 保存（1〜2日）★新規

**ゴール**: 生成データを日付キーで永続化。

**学ぶこと**

- D1（SQLite）の binding とマイグレーション。
- 日付別クエリ設計。

**作るもの（自分で書く）**

- スキーマ: `daily_digest`(日付) / `articles`(記事＋要約＋ソース種別) / `comment_summaries`。原文本文・コメント原文のカラムは持たない（ADR 0003）。
  - **ソース種別カラムを最初から持たせる**（Phase 7 の複数ソース対応の布石）。
  - **記事の一意キーは当面 HN item id**。正規化URLカラムは持つが正規化ロジックは Phase 7（横断dedup が要件化してから）。
  - 閾値・件数・モデル等は**設定値**（vars / 設定テーブル）で外出し。Neuron 累積を記録するテーブルは予算ガバナー（Phase 4以降の後付け）の布石として検討。
- Cron 実行末尾で当日キーに upsert 保存。**ダイジェストは初出基準**（その日に初めて記録された記事の集合）。

**つまずきポイント**

- 過剰設計回避。迷ったら KV「日付→JSON」から始め、クエリ要件が出たら D1 へ移行も可。
- 冪等性: 同日2回実行で重複しないよう upsert。
- **記事は要約成功時にのみ記録（seen）**。失敗記事は未記録のまま残り、翌実行でまだ上位にあれば自然に再処理される（専用リトライ機構は持たない）。

**Claude Code**: **プランモードでスキーマ設計を壁打ち**。「複数ソースを将来足す前提で、このテーブル設計に穴はある？」を計画段階でレビューさせる。ここは設計判断なのでエージェントの指摘が活きる。**SQLは自分で書く。**

**完了の目安**: Cron実行でその日のデータが読み出せる形で保存される。

## Phase 5: Cron 自動化 + 自分用通知（1〜2日）★新規

**ゴール**: 毎日定刻に取得〜保存が自動実行され、完了時に自分の Slack/Discord に通知。

**学ぶこと**

- `wrangler.jsonc` の `triggers.crons` と `scheduled()` ハンドラ（`fetch()` とは別物）。
- ローカルでの scheduled テスト。
- Webhook 通知（Slack/Discord の incoming webhook に `fetch` で POST するだけ）。

**作るもの（自分で書く）**

- `scheduled()` に「取得→本文抽出→翻訳・要約→保存」を実装。
- 末尾に `notify()`: 「当日分を生成。**成功N件 / 失敗M件**」を自分用 Webhook へ POST（成功/失敗件数を載せ観測性にする）。
  - **これは『自分1本に流すだけ』。ユーザー購読型の配信は作らない**（プロダクトの性格を変えるため範囲外）。

**つまずきポイント**

- UTC基準。日本時間の希望時刻から逆算。
- 実行時間はほぼ問題にならない。無料プランは **wall-clock 明示上限なし**、CPU は Cron（間隔≥1h）で15分budgetだが AI/fetch 待ちは CPU を消費しない。**効く制約は外部サブリクエスト50/実行**（Algolia 構成で回避済み）。
- Webhook URL はシークレット（`wrangler secret`）で管理。コードに直書きしない。

**Claude Code**: `scheduled()` の仕様とローカルテスト方法を調査。通知の失敗時挙動（通知が落ちても本処理は成功扱いにする等）の設計を相談。

**完了の目安**: 定刻実行で当日分が自動生成・保存され、自分に通知が届く。

## Phase 6: Hono 配信（1〜2日）

**ゴール**: 保存データを日付別 HTML ページで配信。

**学ぶこと**

- Hono ルーティング: `/`(最新日) と `/:date`。
- Hono JSX でのSSR。
- 各記事に原典リンクを必ず付ける（著作権設計）。

**作るもの（自分で書く）**

- 最新日／日付別ページ、前日・翌日ナビ。
- 表示は「日本語タイトル＋要約＋コメント論点要約＋原典リンク＋HN議論スレッドリンク」。本文・原文は出さない（ADR 0003）。

**つまずきポイント**

- データの無い日付は404か直近へ。
- 最初は動的生成でよい。**過去日のダイジェストは初出基準ゆえ不変（immutable）**なので、後で過去日を強キャッシュ（`Cache-Control: immutable` / Cache API）。変わるのは当日のみ。

**Claude Code**: 書いたページのレビュー。表示に原文が混入していないか（著作権チェック）を観点に含めてレビューさせる。

**完了の目安**: ブラウザで日付を辿って読める。

## Phase 7: 複数ソース拡張（RSS）（2〜3日）★拡張の山場

**ゴール**: Zenn または AWS Blog を2つ目のソースとして追加し、取得層を共通インターフェースに抽象化する。ここが「RSSアグリゲータ」要素の本体。

**重要: ここで初めて抽象化する。** Phase 1〜6 は HN 単体で貫通させ、**具体が動いてから**取得層を切り出す。1ソースしか無いうちに抽象化しない（間違える）。HN と Zenn という2つの具体が揃って初めて、正しい抽象が見える。

**学ぶこと**

- RSS/Atom フィードのパース（Zenn / AWS Blog は公式フィード提供）。
- 取得アダプタの共通インターフェース設計。
  ```
  interface SourceAdapter {
    fetchItems(): Promise<RawItem[]>   // {title, url, body?, comments?, source}
  }
  // HNAdapter（専用API・コメント有） / RSSAdapter（フィード・コメント無）
  ```
- 後段（翻訳・要約・保存・配信）は変えずに、取得層だけ差し替わることを実証。

**作るもの（自分で書く）**

- `HNAdapter` を既存コードからリファクタして切り出し。
- `RSSAdapter` を新規実装（Zenn か AWS Blog）。
- `scheduled()` で複数アダプタを回し、ソース種別を付けて保存。
- 配信でソース別フィルタ or 混在表示。

**つまずきポイント**

- コメントの有無がソースで違う（HNのみ有）。データモデルで `comments` をオプショナルに。
- フィードのフォーマット差（RSS 2.0 / Atom）。
- リファクタで HN の挙動を壊さないこと。Phase 1〜6 が動く状態を保つ。

**Claude Code**: **プランモードでアダプタ抽象化の設計をレビュー**させる。「HNとRSSの差をこのインターフェースで吸収できる？漏れは？」が好適。リファクタ計画を自分でレビューしてから着手。**実装は自分で書く。**

**完了の目安**: 「アダプタを1つ足すだけで3ソース目が増える」状態。複数メディアの日本語要約が1サイトに並ぶ。

## 最初の一歩

Phase 0 → 1。「HN API から記事が取れる」まで動かすと、Phase 2 の要約で試す入力が揃い、手応えも早い。複数ソース（Phase 7）は魅力的だが、HN 単体を1周してから。抽象化は具体が2つ揃ってから——これだけは順序を守る。
